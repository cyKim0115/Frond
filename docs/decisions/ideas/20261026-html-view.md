# Idea Evaluation — HTML 문서 열기 (크로미움 탑재 vs 기존 WebView2)

- Date: 2026-10-26
- Idea id: `20261026-html-view`
- Status: `decided`
- Verdict: `ADOPT_WITH_CHANGES` (HTML 보기, 기존 WebView2) · `REJECT` (크로미움 별도 탑재)
- Related: 조사 보고서 [`Frond HTML 문서 열기`](../../research/reports/Frond%20HTML%20문서%20열기.md) · 근거 노트 `docs/research/research_notes/Frond HTML 문서 열기/` · 결정 D1(Markdown 원문 HTML 허용 목록, [`20261001-v1-open-decisions`](20261001-v1-open-decisions.md)) · [`20260929-stack`](20260929-stack.md)

## Proposal (user)

- 2026-10-26: "이 프로그램에서 html도 열 수 있게 하기엔 비효율적일까? 크로미움 같은 걸 탑재한다면 말야." 퍼플렉시티 딥리서치로 비슷한 사례를 조사해 진행해 달라고 했다

## Context

- Goal of this pass: `.html`·`.htm`을 Frond 탭에서 연다. 엔진을 더 넣어야 하는지와, 남이 만든 HTML을 앱 권한과 어떻게 떼어 놓는지 정한다
- Constraints:
  - Tauri 2.12 + WebView2(이 PC 155, 설치기 최소 150)는 이미 Chromium이다
  - 파일 I/O는 Rust(frond-core)를 거친다
  - 앱 CSP는 `script-src 'self'`(인라인 금지)다
  - Tauri 권고문 GHSA-57fm-592m-34r7: Windows에서 **같은 origin iframe은 invoke에 닿는다**
  - Tauri는 앱이 등록한 커스텀 프로토콜을 로컬 origin으로 본다(`is_local_url`)
  - Store 배포를 앞두고 있다
  - 사용자 HTML 285개 중 56%가 `<script>`를 담고 있다

## Scores

| Axis | Result | Evidence |
|------|--------|----------|
| Feasibility | Pass | WebView2 iframe 두 방식을 헤드리스 Edge 155로 쟀다. 스크립트 없는 같은 origin frame에서 부모 리스너·Highlight·zoom이 되고, 불투명 origin frame에서 부모 DOM·저장소·옆 파일 fetch가 막힌다. Tauri 2.12 소스로 IPC 거부 조건(invoke 키·`Origin`·메인 frame 전용 스크립트)을 확인했다 |
| Direction fit | Partial | "Markdown 뷰어·편집기" 정체성에서 한 발 넓어진다. 대신 사용자가 AI로 만드는 HTML 보고서를 같은 탭·세션·폴더 트리에서 본다. `.html` 기본 앱은 가져오지 않아 브라우저와 다투지 않는다 |
| Efficiency | Pass (WebView2) / Fail (Chromium 탑재) | WebView2 재사용은 배포 크기 +0이다. Electron·CEF·Qt WebEngine은 +55~180 MB에 크로미움 패치 책임이 따르는데, 격리 문제는 그대로 남는다 |

## Alternatives considered

| Alternative | Pros | Cons | Better when |
|-------------|------|------|-------------|
| 크로미움(CEF·Electron·Qt WebEngine) 탑재 (사용자 질문) | 엔진 버전을 앱이 고정 | 설치본 수십~백수십 MB 증가, 크로미움 보안 패치를 직접 추적, 같은 엔진을 두 벌 띄움, 격리 문제는 그대로 | WebView2가 없는 플랫폼을 지원해야 할 때 |
| 브라우저로 넘기기만 | 가장 쉽고 충실도 최고, 앱 위험 0 | 앱 안에서 못 봄(탭·세션·트리·소스 편집 불가) | HTML을 가끔만 볼 때 — 이번 설계에도 늘 있는 버튼으로 둔다 |
| 정화(DOMPurify) 후 앱 DOM에 삽입 | 통합이 쉽다 | 남의 HTML이 앱 권한 문맥에 들어간다(MarkText·Typora 사고 부류), 문서 CSS가 앱과 섞이고 스크립트는 불가 | 짧은 HTML 조각(지금 Markdown 원문 HTML, D1) |
| 아무것도 허용하지 않은 `sandbox` iframe (딥리서치 권장) | 가장 강한 격리 | 앱이 frame 안을 못 만진다. 링크 가로채기·단축키(포커스가 frame에 갇힘)·찾기·줌·인쇄를 못 한다 | 미리보기 창처럼 보기만 할 때 |
| **안전 보기 = 같은 origin·스크립트 없는 iframe + 스크립트 허용 = 불투명 origin iframe(문서별) + 브라우저로 열기** | 통합(링크·단축키·찾기·줌·인쇄), 충실도(스크립트 문서도 앱 안에서), 격리 | 안전 보기는 Chromium 샌드박스가 스크립트를 막는다는 데 기댄다 → 네 겹 방어로 보강 | 지금 |
| 별도 `WebviewWindow` (IPC 권한 없음) | 강한 격리, 네이티브 줌·인쇄 | 탭 밖 창이고 렌더링 문맥이 하나 더 | 신뢰 모드를 창으로 빼고 싶을 때 |
| 창 안 자식 웹뷰 (`add_child`) | 탭 안에서 강한 격리 | `unstable`, 네이티브 웹뷰가 DOM 팝업·메뉴를 가린다 | Tauri가 안정화하고 겹침이 풀릴 때 |

## Decision

- Verdict: 크로미움 탑재 `REJECT`, HTML 보기 `ADOPT_WITH_CHANGES`
- What we will do now:
  1. `.html`·`.htm`을 문서로 연다. 열기 필터·끌어다 놓기·폴더 트리·최근 파일·세션·Markdown 안 링크로 연다. 소스(Ctrl+/)·분할(Ctrl+Shift+/)은 기존 CM6에 HTML 문법 색을 입히고, 저장·인코딩·줄바꿈 보존·초안·외부 변경은 공통 경로를 그대로 쓴다
  2. **안전 보기(기본)**: `<iframe sandbox="allow-same-origin allow-modals" srcdoc>`
     - 스크립트는 네 겹으로 막는다. ① 샌드박스 ② `srcdoc` 맨 앞 meta CSP `script-src 'none'` ③ 앱 CSP 상속(인라인 금지) ④ DOM에서 `<script>`·`on*` 속성·`javascript:` URL·meta refresh·`<base>`를 지운다
     - 이미지·CSS·글꼴·미디어는 문서 폴더(`htmlview` 프로토콜)와 `data:`만 받는다. 외부 리소스는 막는다(열람 추적 방지)
     - 앱이 frame 문서에 직접 붙는다
       - 링크: `http(s)`·`mailto`는 기본 브라우저, `.md`·`.html`은 Frond 탭, `#조각`은 frame 안 이동
       - 그 밖에 단축키·찾기·줌·인쇄·글자 수
  3. **스크립트 허용**(문서별, 설정 `HTML 스크립트` = 묻기(기본)/항상): `<iframe sandbox="allow-scripts allow-modals" src="http://htmlview.localhost/<토큰>/<파일>">`
     - 불투명 origin이라 `Origin: null`을 Tauri가 거부하고, frame의 postMessage는 앱 IPC 처리기에 닿지 않는다. Windows wry는 Tauri 초기화 스크립트(invoke 키 포함)를 frame에도 넣지만, 위 둘 때문에 부르지 못한다(2026-10-26 실측)
     - 헤더 CSP로 `https:` 외부 리소스를 허용하되 `ipc.localhost`·`asset.localhost`는 뺀다
     - 링크·단축키·인쇄는 서버가 주입한 작은 도우미 스크립트의 `postMessage`로 받는다. 앱은 보낸 frame을 확인하고, 탭·외부 열기는 사용자 활성화가 있고 포커스가 그 frame에 있을 때만 받는다. 링크는 `href` 원문을 안전 보기와 같이 문서 폴더 기준으로 판정한다(`../a.md` 포함)
  4. `htmlview` 커스텀 프로토콜(Rust)
     - 문서마다 추측할 수 없는 토큰을 주고 문서 폴더 하나만 연다
     - 경로는 구성 요소별로 디코드하고 `..`·드라이브·`:`·`\`를 거부한다. `canonicalize`한 뒤 구성 요소 단위로 포함 여부를 본다
     - 일반 파일만, 크기 상한, MIME, `nosniff`, `no-store`
     - CORS 헤더는 주지 않는다 — 스크립트가 옆 파일을 읽지 못한다
     - 본문은 앱이 넘긴 편집 중 텍스트로 낸다(분할 뷰 미리보기)
  5. 앱 CSP에 `frame-src`·`media-src`를 새로 두고 `img`·`style`·`font`에 `http://htmlview.localhost`를 더한다. `frame-src`는 frame이 스스로 가는 이동을 막지 못하므로(릴리스 실측), WebView2 frame `NavigationStarting`으로 HTML 탭 frame이 프로토콜·`srcdoc`·빈 frame 밖으로 가면 취소한다(`htmlview.rs` `guard_frames`)
  6. 막은 것이 있으면 배너로 알린다([스크립트 허용]·[브라우저로 열기]). 허용한 문서는 [안전 보기로] 되돌린다. 상태바 모드 메뉴·탭 메뉴·문서 메뉴에 '브라우저로 열기'를 두고, HTML 문서에서는 'HTML로 내보내기'를 숨긴다
- What we will not do:
  - 크로미움 탑재
  - `.html` 기본 앱 가져오기·파일 연결 등록
  - 정화한 HTML을 앱 DOM에 넣기
  - 스크립트 허용 모드의 찾기·목차, HTML 목차, 분할 뷰 스크롤 동기
  - 허용 여부를 파일 경로별로 영구 기억하기(설정 '항상'만 둔다)
- Modified approach (`ADOPT_WITH_CHANGES`):
  - 딥리서치 권장(맨 `sandbox`)과 달리 안전 보기는 `allow-same-origin`을 켠다. 근거는 셋이다
    - 앱이 frame을 만질 수 있어야 링크·단축키·찾기·줌·인쇄가 된다
    - foliate-js·Readest도 같은 origin + 스크립트 차단으로 간다
    - Chromium에는 WebKit 버그 218086이 없음을 실측했다
  - 대가는 "스크립트가 한 줄이라도 돌면 IPC가 열린다"는 전제다. 그래서 네 겹으로 막는다
  - 스크립트를 켜는 모드는 반드시 불투명 origin으로 둔다

- Spec / implementation owner: 에이전트 — 기능 브랜치 `feat/html-view`(임시 워크트리 `../MdEditor-html-view`). 실기 항목은 `next-session.md` §2
- Revisit when:
  1. Chromium 샌드박스 스크립트 차단을 우회하는 CVE가 나오면 안전 보기를 불투명 origin으로 바꾼다(통합 기능은 포기). Tauri·wry를 올릴 때는 E2E 공격 시험(근거 노트 `codebase_and_measurements.md` §4)을 다시 돌린다 — Windows에서 frame에도 들어가는 invoke가 `Origin`·postMessage 경로 분리로 막히는지
  2. Tauri 창 안 여러 웹뷰가 안정화되고 DOM 겹침이 풀리면 다시 본다
  3. 사용자가 탐색기 '연결 프로그램' 목록 등록을 원하면 따로 정한다. AI 훅의 HTML 넘기기는 2026-10-26 사용자 지시로 켰다 — `integrations/open-new-md.ps1`이 `.html`·`.htm`도 넘기고, Claude Code `Write(*.html)`·`Write(*.htm)` 처리기와 Cursor `afterFileEdit` 훅을 더했다([`integrations/README.md`](../../../integrations/README.md))
  4. HTML 탭 메모리가 문제 되면 오래 안 본 frame을 비운다
